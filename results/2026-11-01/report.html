KV-cache quantization × long context: 5 models at f16 / q8_0 / q4_0

Compressing the key/value cache changed one arm by a large margin, made decoding slower everywhere, and left every other difference below what the test could resolve. Gemma at q4_0 was the one large change: its code score dropped to 41 of 100, against 89 at f16, and the cause was truncation at the token cap rather than wrong code, because three of six tasks hit the ceiling and repo_fix wrote 20,459 tokens with no file block. The quantized cache also decoded 17–28% slower than f16 on every model, so it bought memory rather than speed. No other difference survived clustering the three repetitions of each task and correcting across 42 arm-by-tier comparisons; every adjusted p was 1.00, and the earlier claim of three separable arms was pseudo-replication, counting the three repetitions of one task as independent observations. The loop probes saw about 1,000 visible tokens each, which was too short to settle whether compression increases looping.

How to read this page
Each grid is one measurement: rows are models, columns are the three KV cache types. A cell's number is that arm's result. Colour always means the same thing: green = best, red = worst. On the retrieval and code grids best means highest; on the two loop grids best means lowest, and those grids are scaled to the observed range so small differences are visible. Each grid prints its own scale. Hover any cell for the exact value.
The loop numbers come in two flavours, and they differ: any verdict includes a compression heuristic that fires on formulaic prose such as a manual generated from twelve fixed rules, while structural repetition counts only samples with a repeated line, repeated n-gram, repeated 200-character block or a repeating tail cycle — i.e. the thing that actually looks like a loop. Read the structural grid as the finding and the "any verdict" grid as an upper bound.
What the tabs hold: Matrix — the verdict, three grids of level-and-change, decode speed, and how often two arms gave the identical answer. Tasks — one dot plot per task: three dots per model, one per KV type, on a 0–100 axis, so overlapping dots mean "the KV type changed nothing here". Loops — structural repetition per arm as bars, then a card for every sample the detector flagged, with the repeated text highlighted.
Three facts that make the numbers honest: differences of a few points are noise; a single code task can swing by tens of points on one design decision, so check the per-task dot plots before reading a score delta as damage; and a score that falls because an arm hit the generation ceiling is truncated output, not wrong output. The prose summary, with the caveats for this run written out, is docs/RESULTS.md.

What we found

No model scored differently from its own f16 arm by more than this test can resolve. gemma4-26b-a4b is the exception: at q4_0 its code score was 41 of 100 against 89 at f16, and it ran out of room on 3 of 6 coding tasks, so it was cut off rather than wrong. On this build the quantized cache was also 17–28 % slower to answer with than f16, so it buys memory, not speed. No cache setting made a model repeat itself more often by a difference this test can resolve.
Best combination on this run: qwen38-flash with a q4_0 cache — 84.9 out of 100, 0/12 structural-loop samples, 12.3 tokens/second, 9107 MiB of graphics memory with 48 layers of the model kept in system RAM.
How sure are we, and how the ranking works
Its lead is not established: 14 other arms, including its own f16 arm, cannot be distinguished from it (task-clustered pairs, Holm over 42 comparisons). Capability = the average of the retrieval score and the code score; ties go to the arm with fewer repeating samples, then to the faster one; every paired test clusters the three reps of a task and corrects across all 42 comparisons, so nothing here can separate on a handful of correlated samples.
